# LearnLab

A lightweight Learning Management System: course authoring, catalog, enrolment, sequential lessons, deterministic quiz grading, progress tracking, an instructor workbench and an admin console.

LearnLab is the AI-Native Engineer capstone **BC-AINE-011**. The application is **deterministic**: grading, progress, course lifecycle and access control behave identically every time, and nothing calls an AI model at runtime. What is AI-native is how it is built — every line of production code, every test and every migration is generated by Claude Code agents through the **Claude Harness Engine** plugin, under the supervision of a human engineer who writes specs, configures agents and reviews merge requests.

## Capstone rules — never break these

1. **No-Hand-Coding.** Agents generate all production code, tests and migrations. Humans edit only specs, CLAUDE.md files, agent / skill / command / hook definitions and other substrate files.
2. **Spec-Is-Truth.** If code and spec disagree, the spec wins. Never change a spec to make a failing test pass — stop and ask the engineer.
3. **PR-Only Merge.** Never commit or push to `main`. Work on `feature/<task-id>-<short-name>`, open a merge request, and merge only with `git merge --no-ff` after CI is green and the engineer approves.
4. **Synthetic Data.** Fictional names and `@example.test` addresses only. No Virtusa confidential or customer data anywhere — code, seeds, tests, fixtures or logs.

## Architecture rules

- **Layers:** `api → services → repositories`; `services → domain`; `services → integrations` (through interfaces only). Imports only go downward.
- **`domain/` is pure.** It imports only the Python standard library — no FastAPI, SQLAlchemy, logging, `core`, or any other LearnLab layer — and never calls repositories.
- **Controllers are thin.** Validate with Pydantic, check role, call one service, map the result. No business rules and no repository imports in `api/`.
- **Six domain rule files** own all business rules: `CourseStateMachine`, `PublishedContentGuard`, `EnrollmentPolicy`, `ProgressCalculator`, `QuizGrader`, `RoleBoundaryPolicy`. Do not re-implement a rule anywhere else.
- Enforced by import-linter contracts and `backend/tests/architecture/` (ARCH-01 – ARCH-07).
- **Harness layer hook:** the harness defaults to `src/<layer>/` with singular names. At `/scaffold`, set `project-manifest.json` → `"architecture": { "layers": ["core", "domain", "integrations", "repositories", "services", "api"], "layer_roots": ["backend/src/learnlab"] }` so the hook checks our layout.

## Domain invariants

| Rule | Detail | Source |
|---|---|---|
| Integer arithmetic only | Scores and progress use `(n × 100) // total`. No `float`, true division `/` or `round()` in `QuizGrader` or `ProgressCalculator`. | NFR-01 |
| Append-only records | Enrolments, lesson completions, quiz attempts and course state changes are insert-only. Their repositories have no update or delete methods. | NFR-02 |
| Append-only migrations | Never edit an existing Alembic revision; add a new one. | NFR-05 |
| No PII or performance data in logs | Never log email, phone, password, scores or progress. | NFR-03 |
| Structured logs | JSON logs with `X-Correlation-ID` on every line and every response. | NFR-06 |
| Auth at the boundary | Every non-public route has a role guard; ownership is checked in services via `RoleBoundaryPolicy`. | NFR-04 |
| Lifecycle | Only the transitions in `specs/catalog_spec.md` §3.1 are allowed; anything else raises `InvalidCourseStateException` → 409. | AC-08 |
| Content lock | Course content changes only while DRAFT or UNPUBLISHED (`PublishedContentGuard`). | DR-05 |
| No grade writes | No route lets anyone create, change or delete a score except a learner submitting an attempt. | NFR-08 |
| Error format | `{"error": {"code", "message"}}` with codes from `specs/app_spec.md` §8.1. | — |

## Testing rules

- **Test first.** For each AC: commit the failing test → commit the smallest implementation → commit any refactor. Three separate commits.
- **Tag every acceptance test** with its AC id: `@pytest.mark.ac("AC-05")` in Python; `AC-05` in the test title for Vitest and Playwright.
- Domain rules are tested with parametrised tables taken from the spec's worked examples.
- Playwright tests run at **375 px** and **1280 px** and keep snapshots in `e2e/__snapshots__/`.
- Coverage reports (`coverage.xml`, `frontend/coverage/lcov.info`) are committed.
- Never skip, delete or weaken a failing test to get green — fix the code or escalate.

## Development workflow

1. Read this file, [AGENTS.md](AGENTS.md) and the `CLAUDE.md` of every folder you will touch.
2. Read the referenced spec section and its AC scenarios.
3. Inspect the existing code.
4. Plan the smallest complete change.
5. Write failing AC-tagged tests and commit them.
6. Implement and commit.
7. Run static checks, unit, API, architecture and Playwright tests.
8. Open a merge request.
9. Report: files changed, ACs satisfied (with test names), tests run and results, coverage, remaining risks.

Commit messages start with the task id and cite the AC: `TASK-S1-03: enforce single enrolment (AC-01)`.

## Quality gates — a merge request is ready only when

- ruff, mypy, eslint and tsc are clean
- all unit, API, architecture and Playwright tests pass
- every AC touched has at least one tagged test
- the harness evaluator report for the sprint is saved in `specs/reviews/`
- the Claude Code review job in CI has no blocking findings
- the engineer has approved

## When to stop and ask the engineer

- A spec is ambiguous, or spec and code disagree
- A change needs a new requirement, endpoint, table or dependency not in the specs
- A test can only pass by weakening it or changing a spec
- A hook blocks you and you believe the hook is wrong
- Anything would touch `main`, an existing migration, or real data

## Out of scope — do not build

Real video streaming, payments, live classes, proctoring, certificates, instructor/admin self-registration, password reset, SSO, reordering or deleting content after first publish, production deployment, and any runtime AI feature. Full list: `specs/app_spec.md` §5.
