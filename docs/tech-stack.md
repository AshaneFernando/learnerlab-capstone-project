| Field | Value |

## 1. Context

LearnLab is built under a **No-Hand-Coding Rule**: every line of production code, test and migration is generated by Claude Code agents, driven by the **Claude Harness Engine** plugin ([cwijayasundara/claude_harness_eng_v5](https://github.com/cwijayasundara/claude_harness_eng_v5)). The engineer writes specifications and guardrails and reviews pull requests.

The capstone brief says the stack itself is not graded. What is graded is the evidence the stack lets us produce: layered architecture, architecture tests, TDD history, coverage reports, Playwright UI tests and CI.

That changes the question. The best stack is not the one a human writes fastest. It is the one **the harness agents generate, check and repair most reliably**, so that the engineer's time goes into specs and review instead of fighting tooling.

## 3. Decision and rationale

### 3.1 Backend — Python 3.12 + FastAPI

- **Harness-native.** `/scaffold` preset A is "Python (FastAPI) + React (Vite)". The code-gen skill ships `stack-python-fastapi.md`, `arch-python-fastapi.md`, `observability-python-fastapi.md` and `tests-python.md`, so agents generate to a known pattern on the first try.
- **Guardrails apply.** The harness `verify-on-save` hook runs `ruff` and `mypy` on every file an agent writes. `layers.js` blocks imports that go the wrong way through the layers (api → service → repository → domain). Both work for Python.
- **Clean layering.** FastAPI's `APIRouter` + `Depends(...)` maps directly onto the required controllers / services / repositories / domain layout, and gives a natural place for the authentication boundary (NFR-04).
- **Domain rules made simple.** Python integers have arbitrary precision, so integer-only quiz scores and progress percentages (NFR-01) are straightforward to implement and to assert in tests.
- **Typed contracts.** Pydantic v2 models validate every request and response, and FastAPI produces an OpenAPI spec for free.

Supporting choices:

| Concern | Choice | Why |
|---|---|---|
| Dependency management | **uv** | Harness default; fast, lockfile-based, reproducible in CI |
| ORM | **SQLAlchemy 2.0** | Typed, well-known to the agents; repository layer wraps it |
| Migrations | **Alembic** | Versioned migration files make the append-only migration rule (NFR-05) easy to enforce with a hook |
| Logging | Structured JSON logging + correlation-ID middleware | Meets NFR-06; harness observability reference covers it |
| Auth | Email + password, role-scoped bearer tokens via a FastAPI dependency | Simple, self-contained, works with synthetic seed users |

### 3.2 Frontend — React + TypeScript (Vite)

- **Harness-native.** Covered by `stack-react-typescript.md`, `arch-react-typescript.md`, `tests-react-typescript.md` and the `react-code` skill. The evaluator has a React verify guide, and the `design-critic` / `ui-designer` agents target it.
- **Meets the frontend requirement.** The brief asks for a React, Angular or Vue frontend with at least one responsive layout. React with a responsive CSS approach covers this.
- **TypeScript** gives `tsc` and `eslint` checks the harness hooks can run on every save.

### 3.3 Database — SQLite (instead of preset A's PostgreSQL)

- The brief requires the app to start **locally with one command**, with seed data. SQLite needs no server, no Docker and no credentials, so it meets this requirement with the least effort.
- The brief explicitly allows in-memory / SQLite databases.
- Access goes through SQLAlchemy, so moving to PostgreSQL later is a configuration change, not a rewrite.
- Trade-off accepted: SQLite handles concurrent writes less well than PostgreSQL. A database-level unique constraint on (learner, course) still guarantees no duplicate enrolments (DR-08) under retries.

### 3.4 Run and build

| Task | Command (to be finalised at scaffold) |
|---|---|
| Install | `uv sync` (backend) · `npm ci` (frontend) |
| Run locally | One root command that applies migrations, loads seed data, and starts the API and the UI |
| Test | `uv run pytest` · `npm test` · `npx playwright test` |

## 4. Test stack

The rubric rewards specific kinds of test evidence, so each tool below is chosen for the evidence it produces and because the harness already knows how to drive it.

| Layer | Tool | What it proves | Rubric item it serves |
|---|---|---|---|
| Backend unit & domain tests | **pytest** | Domain rules (grading, progress, lifecycle, enrolment, access) behave as specified | ≥20 unit tests; quiz grading, progress, role-boundary and state-transition tests |
| Backend API tests | **pytest + FastAPI `TestClient` / `httpx`** | Endpoints enforce roles, return correct status codes and honour each AC end-to-end at the API level | AC-tagged tests; NFR-04 |
| AC traceability | **pytest markers** (e.g. `@pytest.mark.ac("AC-05")`) plus `AC-NN` in test names | Every acceptance criterion has at least one test, and a script can list which | "Every AC has ≥1 test" |
| Coverage | **pytest-cov** → `coverage.xml` (backend), **Vitest coverage (v8)** → `lcov.info` (frontend) | How much code the tests exercise; reports are committed | Coverage artefact + tool declared in dependencies |
| Architecture tests | **import-linter** contracts + pytest tests in `tests/architecture/` | Layers only import downward; the domain has no framework imports; controllers never touch repositories directly | ≥3 structural tests; layering tool configured |
| Architecture rule tests (NFR-08) | **pytest** in `tests/architecture/` | Instructors can't change grades for their own learners; learners can't read others' progress; published courses can't be changed without unpublishing | NFR-08 |
| Frontend component tests | **Vitest + React Testing Library** | UI components render and behave correctly | Unit test count; frontend evidence |
| End-to-end / UI | **Playwright** (test runner) + **Playwright MCP** (used by the harness evaluator) | Real user journeys work in a browser; screenshot snapshots catch visual regressions; responsive layout is checked at mobile and desktop widths | Playwright with a snapshot directory; MCP configured and used |
| Static checks | **ruff**, **mypy** (backend) · **eslint**, **tsc** (frontend) | Code is lint-clean and type-correct before tests even run | Run on every save by harness hooks and in CI |

### 4.1 Why these test tools in particular

- **pytest** is the harness's Python test runner (`tests-python.md`). It has fixtures for seeded data, `parametrize` for the many edge cases in grading and progress maths, and markers for AC tagging.
- **import-linter** is one of the three tools the brief names for layering rules. The harness's own `layers.js` hook already blocks bad imports while agents write code. import-linter adds a *declared, versioned contract* that CI and the reviewer can see. One stops mistakes as they happen; the other proves the rule is in force.
- **pytest-cov** produces `coverage.xml`, one of the artefact formats the brief accepts, and is declared as a dev dependency so the reviewer can find it.
- **Vitest** is the native test runner for Vite projects and is covered by the harness's `react-code` skill (`vite-and-testing.md`). It shares Vite's config, so there is no separate Jest/Babel setup for agents to get wrong.
- **Playwright** is required by the brief and is what the harness evaluator uses through Playwright MCP (`test-playwright.md`, `playwright-patterns.md`). Using the same tool for committed E2E tests and for the evaluator's live checks means one set of selectors and patterns.

### 4.2 How TDD is evidenced

Agents follow red → green → refactor for each acceptance criterion:

1. Commit a failing test tagged with the AC ID (red).
2. Commit the minimal implementation that makes it pass (green).
3. Commit any clean-up with tests still passing (refactor).

The harness git hooks and the TDD support in its gate library help enforce this order. The commit history then shows it, which the rubric checks (≥10 test files showing the pattern). Details and a worked example (AC-05 quiz grading) will be in `docs/tdd.md`.

## 5. CI

**GitLab CI** (Virtusa's preferred platform) with the **Claude Code Action** (or equivalent Claude Code CI step) wired in. Pipeline stages:

1. Lint and type-check
2. Unit tests, API tests and architecture tests, with coverage
3. Frontend tests with coverage
4. Playwright E2E
5. Claude review of the merge request

## 6. Consequences

**Positive**
- The harness's scaffold, code-generation references, evaluator guides and save-time hooks all apply, so most guardrails are already in place on day one.
- Every rubric item that needs a test artefact maps to a specific tool.
- One-command local start with no infrastructure.

**Negative / accepted risks**
- Two languages (Python and TypeScript) means two toolchains to keep in sync in CI.
- SQLite limits write concurrency; fine for a local, single-user-at-a-time evaluation build.
- Diverging from preset A's PostgreSQL means one profile change at scaffold time.

## 7. Revisit if

- The platform needs multi-user production load → move to PostgreSQL (configuration change via SQLAlchemy).
- The team's review skill is much stronger in another language → reconsider the Express + React preset, which keeps harness support.
