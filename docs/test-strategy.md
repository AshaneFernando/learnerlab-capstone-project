## 1. Test levels

| Level | Tool | Location | What it proves | Speed |
|---|---|---|---|---|
| **A. Domain unit** | pytest, `parametrize` | `backend/tests/unit/domain/` | The six pure domain rule files behave exactly as the spec tables say | ms |
| **B. Service** | pytest + in-memory SQLite fixture | `backend/tests/unit/services/` | Orchestration: ownership checks, repository calls, transactions, snapshots, idempotency | fast |
| **C. API** | pytest + FastAPI `TestClient` / `httpx` | `backend/tests/api/` | Status codes, error codes, error shape, role guards and every AC scenario end-to-end at HTTP level | fast |
| **D. Architecture** | import-linter contracts + pytest | `backend/tests/architecture/`, `backend/.importlinter` | Layering, domain purity, append-only repositories, no float maths, every route guarded, NFR-08 boundaries | fast |
| **E. Frontend component** | Vitest + React Testing Library | `frontend/src/**/*.test.tsx` | Components render the right state (locked lessons, read-only editor, enabled lifecycle buttons, band cards) | fast |
| **F. End-to-end UI** | Playwright | `e2e/*.spec.ts`, `e2e/__snapshots__/` | Real journeys in a browser at **375 px** and **1280 px**, with committed screenshot snapshots | slow |

The harness **evaluator** additionally drives the running app through Playwright MCP each sprint and writes its verdict to `specs/reviews/sprint-N-evaluation.md`. That is a sprint gate, not a replacement for level F.

## 2. AC tagging convention

| Where | Convention | Example |
|---|---|---|
| pytest | Marker `ac` registered in `backend/pyproject.toml` under `[tool.pytest.ini_options] markers`, run with `--strict-markers` so a typo fails the run | `@pytest.mark.ac("AC-05")` |
| pytest (scenario) | Scenario id in the test name | `test_ac_05_4_grading_formula` |
| Vitest | AC id at the start of the `it` / `describe` title | `it("AC-07.11 shows every lesson locked when unpublished", …)` |
| Playwright | AC or UI-AC id at the start of the `test` title | `test("AC-01.3 learner enrols from the catalog", …)` |
| NFR scenarios | Same marker with the NFR scenario id | `@pytest.mark.ac("NFR-03.1")` |

A test may carry several tags. `/ac-coverage` and `scripts/ac_audit.py` read these tags to prove that every AC-NN and NFR-NN.x has at least one test.

## 5. Golden cases

`specs/fixtures/golden_cases.json` holds the expected results for every domain rule (grading table, progress table and bands, all 12 lifecycle cells, enrolment cases, permission matrices, lesson order). Domain tests (level A) and the matching API tests load it and are **parametrised from it**, so the spec tables, the fixture and the tests cannot drift apart. A change to an expected value is a spec change (Spec-Is-Truth): update the spec, then the fixture, then let the agents regenerate.

## 6. Coverage

| Target | Threshold | Artefact (committed) |
|---|---|---|
| Backend overall | ≥ 80% lines | `backend/coverage.xml` (pytest-cov) |
| Backend `domain/` | ≥ 90% lines | same report |
| Frontend | reported, no gate | `frontend/coverage/lcov.info` (Vitest, v8) |

`pytest-cov` and `@vitest/coverage-v8` are declared as dev dependencies. The CI job `test-backend` fails below threshold (NFR-11.1). Coverage artefacts are excluded from `.gitignore` on purpose so the reviewer can see them.

## 7. Critical failures — always block a merge

1. Any `float`, true division `/`, `round(`, SQL `AVG(` or `REAL` in grading or progress code, or a non-`int` percentage field (NFR-01).
2. A duplicate enrolment, completion or state transition under retry or concurrency (AC-01.6, AC-07.12, AC-08.6).
3. Any update or delete path on enrolments, completions, attempts, snapshots or state changes (NFR-02).
4. Any route an instructor can call that writes a score, attempt or completion (AC-06.5, AC-09.7).
5. A learner reading another learner's progress or attempts (AC-07.9).
6. A content change accepted on a PUBLISHED or ARCHIVED course (AC-03.3).
7. Email, phone, password, score or progress in a log line or echoed in an error body (NFR-03).
8. An edited existing migration (NFR-05).
9. A non-standard error body or a stack trace in a response.
10. An AC or NFR scenario with no tagged test, or a skipped / `xfail` acceptance test.
11. Coverage below threshold.

## 9. Environment-first rules

Most flaky failures come from the environment, not the code. Agents check these before changing code, and record what they find in `docs/post-mortems/` when one is the cause.

| Rule | Detail |
|---|---|
| SQLite settings | Every connection enables WAL mode and `busy_timeout = 5000` ms (EN-3). Concurrency tests use a file-based database, not `:memory:`, because in-memory databases are per-connection. |
| Test isolation | Each test gets a fresh database (temporary file + migrations applied, or a transaction rolled back after the test). No test depends on another test's data or order. |
| Time | All timestamps come from the injectable `core.clock.Clock`; tests use a fixed or stepping fake clock. Never `sleep` to separate timestamps. |
| No network | Tests make no outbound calls. `VideoProvider` and `PaymentProvider` use their stubs. Playwright runs against the local app only. |
| Determinism | No random data without a fixed seed; parametrised tables come from the spec or `golden_cases.json`. |
| Clean start | CI starts from a clean checkout so `smoke-start` catches anything that only works on a developer machine. |

## 10. Test data rules

- Synthetic only: fictional names, `@example.test` email addresses, phone numbers in an obviously fake range (e.g. `+44 7700 900xxx`).
- Test users and courses are built with small factory helpers in `backend/tests/conftest.py`; tests never rely on seed data except the smoke and E2E tests.
- No Virtusa or customer data anywhere — enforced by NFR-10.1.
