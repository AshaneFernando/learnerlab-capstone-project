# LearnLab — Business Case

| Field | Value |
|---|---|
| Business case ID | BC-AINE-011 |
| Domain | EdTech — Online Learning |
| Product | LearnLab, a lightweight Learning Management System (LMS) |
| Delivery model | AI-native: all production code generated by Claude Code agents under human supervision |
| Data policy | Synthetic data only |

---

## 1. Problem

An online learning provider wants to put structured courses in front of learners without buying or running a heavyweight LMS. Today, course content lives in scattered documents and videos. There is no single place where:

- instructors can build a course as an ordered set of modules and lessons,
- an administrator can decide what is visible to learners and when,
- learners can enrol, work through material in order and see how far along they are,
- learners can check their understanding with quizzes that are marked instantly and consistently,
- instructors and administrators can see whether learners are actually progressing.

Without this, instructors cannot tell who is stuck, learners have no sense of progress, and quiz marking is manual, slow and inconsistent.

The provider needs a small, trustworthy platform that covers the core learning loop — **publish → enrol → learn → assess → track** — and nothing more. Video streaming and payments are explicitly not needed for the first release and are stubbed.

## 2. Target users

| Role | Who they are | What they need from LearnLab |
|---|---|---|
| **Learner** | A registered individual taking one or more courses | Find a relevant course, enrol once, move through lessons in order, take quizzes as often as they like, and see their own progress and best scores. |
| **Instructor** | A subject-matter expert who authors and owns courses | Create a course, structure it into modules and lessons, write quiz questions, and see how their learners are progressing — without being able to tamper with grades. |
| **Admin** | A platform operator responsible for the catalog | Decide which courses are live (publish / unpublish / archive), keep the catalog tidy, and monitor enrolment and engagement across the platform. |

Each user has exactly one role. Roles are separated at the API boundary; a user can never act outside their role.

## 3. Value proposition

- **For learners:** one place to discover courses, a clear path through each one, instant quiz feedback, and an honest progress percentage.
- **For instructors:** fast course authoring with a simple course → module → lesson structure, plus an at-a-glance view of where learners are in their course (progress bands), so they can step in early.
- **For the provider:** a controlled catalog (nothing reaches learners until an admin publishes it), consistent, auditable grading, and engagement analytics — delivered on a lightweight platform that is cheap to run and change.
- **For the engineering organisation:** a reference example of an AI-native delivery where specifications, guardrails and review — not hand-written code — are the engineer's output.

## 4. Scope

### 4.1 In scope (first release)

| Capability | Summary |
|---|---|
| **Course catalog** | Browse and search published courses by category and difficulty. |
| **Course authoring** | Instructors create courses (title, description, category, difficulty), add modules, and nest lessons inside modules. |
| **Course lifecycle** | Courses move through DRAFT → PUBLISHED → UNPUBLISHED → ARCHIVED under admin control. |
| **Enrolment** | Learners register and enrol in published courses — one enrolment per learner per course. |
| **Lesson delivery & progress** | Learners work through lessons in order, mark them complete and see a progress percentage. Video is a stub (placeholder URL / embed). |
| **Quiz engine** | Module-end quizzes with multiple-choice (single correct answer) and True/False questions, auto-graded deterministically; unlimited attempts; best score kept. |
| **Instructor workbench** | Author content and quiz questions; view learner progress aggregated into bands per course. |
| **Admin console** | Manage the catalog, publish/unpublish/archive courses, and view enrolment and engagement analytics. |

### 4.2 Out of scope

- Real video streaming or CDN integration — a stub `VideoProvider` interface returns placeholder references
- Real payment gateway and paid courses — a stub `PaymentProvider` interface exists and treats every course as free
- Live virtual classes (WebRTC)
- Proctoring or anti-cheat technology
- Certificate generation and external verification
- Production deployment, secret management, multi-region hosting

## 5. Domain rules

These rules are the heart of the product. Each will be implemented as an explicit rule / policy / validator in `src/domain/` and covered by tests.

| Domain rule file | Rules | Purpose |
|---|---|---|
| `CourseStateMachine` | DR-01 – DR-04, DR-06 | Allowed lifecycle transitions and publish preconditions |
| `PublishedContentGuard` | DR-05 | Blocks content changes unless the course is DRAFT or UNPUBLISHED |
| `EnrollmentPolicy` | DR-07 – DR-10 | Who can enrol, when, and only once |
| `ProgressCalculator` | DR-11 – DR-15 | Sequential completion, integer progress %, progress bands |
| `QuizGrader` | DR-16 – DR-21 | Question shape, integer grading, attempts, best score |
| `RoleBoundaryPolicy` | DR-22 – DR-26 | Role separation and ownership checks |

### 5.1 Course lifecycle (`CourseStateMachine`, `PublishedContentGuard`)

| ID | Rule |
|---|---|
| DR-01 | A newly created course is always in **DRAFT**. |
| DR-02 | Allowed transitions: DRAFT → PUBLISHED, PUBLISHED → UNPUBLISHED, UNPUBLISHED → PUBLISHED (republish), UNPUBLISHED → ARCHIVED. |
| DR-03 | Any other transition (e.g. DRAFT → ARCHIVED, ARCHIVED → anything, PUBLISHED → DRAFT) is rejected with `InvalidCourseStateException`. |
| DR-04 | Only an **admin** may change a course's lifecycle state. |
| DR-05 | A course's content (details, modules, lessons, quiz questions) may only be edited in **DRAFT** or **UNPUBLISHED**. A PUBLISHED course must be unpublished before it can be changed. ARCHIVED courses are read-only. *(PublishedContentGuard)* |
| DR-06 | A course cannot be published unless it has at least one module containing at least one lesson. |

### 5.2 Enrolment (`EnrollmentPolicy`)

| ID | Rule |
|---|---|
| DR-07 | A learner may enrol only in a **PUBLISHED** course. |
| DR-08 | A learner may hold at most **one** enrolment per course. A second request (including a retried or concurrent request) must not create a duplicate. |
| DR-09 | Enrolment records are **append-only**: they are never updated in place or deleted. |
| DR-10 | Unpublishing or archiving a course does not remove existing enrolments; enrolled learners keep read access to their history and progress, but no new enrolments are accepted. |

### 5.3 Lesson progress (`ProgressCalculator`)

| ID | Rule |
|---|---|
| DR-11 | Only an enrolled learner can mark a lesson complete in that course. |
| DR-12 | Lessons are completed in sequence: a learner can only complete a lesson once the previous lesson in the course order is complete. |
| DR-13 | Completing an already-completed lesson has no further effect (one completion record per learner per lesson). Completion records are **append-only**. |
| DR-14 | Course progress = `completed_lessons × 100 ÷ total_lessons`, using **integer arithmetic** (rounded down). A course with no lessons has 0% progress. |
| DR-15 | Progress bands used for reporting: **0–24%**, **25–49%**, **50–74%**, **75–100%** (each learner falls into exactly one band). |

### 5.4 Quiz grading (`QuizGrader`)

| ID | Rule |
|---|---|
| DR-16 | Supported question types: **MCQ** (exactly one correct option) and **TRUE/FALSE**. A question that doesn't meet this shape cannot be saved. |
| DR-17 | Score = `correct_answers × 100 ÷ total_questions`, using **integer arithmetic** (rounded down). Floating-point is never used. Unanswered questions count as incorrect. |
| DR-18 | Grading is deterministic: the same answers to the same quiz always produce the same score. |
| DR-19 | A learner may attempt a quiz any number of times. Each attempt is timestamped and stored **append-only**. |
| DR-20 | The learner's recorded result for a quiz is their **best** score across all attempts. |
| DR-21 | Only an enrolled learner may attempt a quiz in that course. A quiz with no questions cannot be attempted. |

### 5.5 Access and roles (`RoleBoundaryPolicy`)

| ID | Rule |
|---|---|
| DR-22 | Authentication and role checks happen at the API (controller) boundary. |
| DR-23 | A learner can see only their **own** enrolments, progress and quiz attempts — never another learner's. |
| DR-24 | An instructor can author and view progress only for courses they own. |
| DR-25 | An instructor cannot grade, regrade, override or edit quiz results for learners in their own courses — grading is done only by the quiz engine. |
| DR-26 | Only admins can publish, unpublish or archive courses and view platform-wide analytics. |

### 5.6 Data protection and audit

| ID | Rule |
|---|---|
| DR-27 | Learner PII (email, phone) and performance data (scores, progress) are never written to logs in plaintext; they are masked or omitted. |
| DR-28 | Every log line is structured JSON carrying a request correlation ID. |
| DR-29 | Database migrations are append-only: an existing migration is never edited; changes are made with a new migration. |
| DR-30 | Only synthetic data is used — seed data is fictional instructors, learners, courses and quizzes. |

## 6. Acceptance criteria (traceability)

Each criterion will be written in Given-When-Then form in the relevant feature spec and must have at least one test tagged with its ID.

| AC | Criterion | Domain rules | Feature spec |
|---|---|---|---|
| AC-01 | Learner can register and enrol in any PUBLISHED course; cannot enrol twice in the same course | DR-07, DR-08 | `enrollment_spec.md` |
| AC-02 | Instructor can create a course with title, description, category and difficulty; it starts in DRAFT | DR-01 | `course-authoring_spec.md` |
| AC-03 | Instructor can add modules and nested lessons to a draft course | DR-05 | `course-authoring_spec.md` |
| AC-04 | Admin can publish or unpublish a course; learners can enrol only in PUBLISHED courses | DR-02, DR-04, DR-07 | `catalog_spec.md` |
| AC-05 | Quizzes support MCQ and TRUE/FALSE and are auto-graded deterministically | DR-16 – DR-18 | `quiz-engine_spec.md` |
| AC-06 | Multiple attempts allowed; best score recorded; attempts timestamped and append-only | DR-19, DR-20 | `quiz-engine_spec.md` |
| AC-07 | Learner can mark a lesson complete; progress = completed ÷ total lessons | DR-11 – DR-14 | `progress-tracker_spec.md` |
| AC-08 | Lifecycle DRAFT → PUBLISHED → UNPUBLISHED → ARCHIVED enforced; invalid transitions raise `InvalidCourseStateException` | DR-02, DR-03 | `catalog_spec.md` |
| AC-09 | Instructor can view learner progress per course grouped into progress bands | DR-15, DR-24 | `instructor-workbench_spec.md` |
| AC-10 | Admin can manage the catalog, approve published courses and monitor enrolment analytics | DR-26 | `catalog_spec.md`, `instructor-workbench_spec.md` (analytics) |

Planned delivery order (one harness sprint each): **Sprint 1** catalog + enrolment (AC-01, 02, 04, 08) → **Sprint 2** modules, lessons, progress (AC-03, 07, 09) → **Sprint 3** quiz engine, instructor workbench, admin analytics (AC-05, 06, 10). See `architecture.md` §10.

## 7. Non-functional requirements

| NFR | Requirement | How we will meet it |
|---|---|---|
| NFR-01 | Quiz scores are integer percentages; no floating-point | Integer-only `QuizGrader`; tests assert integer results; a check flags `float` in the grading module |
| NFR-02 | Quiz attempts, lesson completions and enrolments are append-only | Insert-only repositories; a hook rejects code that updates or deletes these records |
| NFR-03 | No plaintext PII or performance data in logs | Log redaction filter; a hook flags PII fields in log calls |
| NFR-04 | Auth boundary at the controller layer; roles separated | FastAPI auth dependencies on every route; role tests per endpoint |
| NFR-05 | Migrations are append-only | Alembic migrations; a hook blocks edits to existing migration files |
| NFR-06 | Structured JSON logs with correlation IDs | Logging middleware sets/propagates `X-Correlation-ID` |
| NFR-07 | Health endpoint returns 200 within 1 s of startup | `/health` endpoint with a timed test |
| NFR-08 | Architecture rules enforced as tests (instructor can't grade own learners; learner can't read another's progress; published courses can't be mutated without unpublishing) | Tests in `tests/architecture/` and domain-level policy tests |

## 9. Assumptions and open decisions

| # | Topic | Assumption taken (to confirm) |
|---|---|---|
| A-1 | Republishing | UNPUBLISHED → PUBLISHED is allowed so that a course can be corrected and put back live. The brief lists the lifecycle as a forward chain only. |
| A-2 | NFR-08 "instructors cannot grade their own courses' learners" | Quizzes are auto-graded, so this is read as: instructors cannot create, change or override any grade or attempt record for learners in their courses. |
| A-3 | Who authors quizzes | The course's owning instructor authors quiz questions, at the end of each module. One quiz per module. |
| A-4 | Sequential lessons | The brief says learners move through lessons "sequentially"; we enforce order (DR-12). |
| A-5 | Approval of published courses (AC-10) | Instructors cannot publish; an admin publishing a course *is* the approval step. |
| A-6 | Authentication | Simple email + password login with role-scoped tokens and seeded synthetic accounts. No SSO or external identity provider. |
| A-7 | Video | Lessons hold text content plus an optional placeholder video reference from the stub `VideoProvider`; no streaming. |
| A-8 | Payments | A stub `PaymentProvider` interface is in place so a real gateway can be added later; in this release every course is free. |
| A-9 | Quizzes and progress | Quizzes do not count towards course progress; progress is based on lessons only. |
| A-10 | Quiz timing | A learner can attempt a module's quiz at any time while enrolled in a PUBLISHED course; finishing the module's lessons first is not required. |
| A-11 | Inactive courses | While a course is UNPUBLISHED or ARCHIVED, enrolled learners can still view their progress, attempts and lesson content but cannot complete lessons or attempt quizzes. |
| A-12 | Replaced quizzes | When a quiz is replaced, earlier attempts keep their own scores and per-question results; best score is the maximum over attempts on every version. |
| A-13 | Progress snapshots | Each new lesson completion appends a progress snapshot as history (brief §6.2); the live percentage is always computed from completions. |

## 10. Glossary

| Term | Meaning |
|---|---|
| Course | A unit of learning owned by one instructor, made of ordered modules. |
| Module | An ordered group of lessons within a course; may end with a quiz. |
| Lesson | The smallest unit of content a learner completes. |
| Enrolment | The record that a learner has joined a course. |
| Attempt | One submission of answers to a quiz, with its score and timestamp. |
| Best score | The highest score across all of a learner's attempts at a quiz. |
| Progress band | One of four ranges (0–24, 25–49, 50–74, 75–100%) used to group learners by progress. |
