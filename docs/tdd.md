# LearnLab — Test-Driven Development

| Field | Value |
|---|---|
| Status | Draft (Prompt 04) |
| Applies to | Every agent that writes production code or tests |

| Rubric evidence | This document + at least 10 test files whose git history shows red → green → refactor |

---

## 1. The cycle

For every acceptance-criterion scenario (AC-NN.x) in scope:

| Step | What the agent does | Must be true before committing |
|---|---|---|
| **Red** | Writes the test(s) for the scenario, tagged with the AC id. Adds only the minimum stubs (empty function, exception class) needed for the test to import. | The new tests **fail for the right reason** (assertion or `NotImplementedError`), not because of a syntax or import error. Existing tests still pass. |
| **Green** | Writes the smallest implementation that makes the new tests pass. | All tests pass. No test was changed in this step. |
| **Refactor** | Improves names, removes duplication, extracts constants — no behaviour change. | All tests still pass. No test assertions changed. Skip this commit if there is nothing to improve. |

Each step is a **separate commit**, so the reviewer can see the order.

## 2. Commit format

```text
TASK-S<sprint>-<nn>: red — <what the tests prove> (AC-NN)
TASK-S<sprint>-<nn>: green — <what was implemented> (AC-NN)
TASK-S<sprint>-<nn>: refactor — <what was tidied> (AC-NN)
```

Example sequence:

```text
TASK-S3-02: red — QuizGrader integer grading table (AC-05)
TASK-S3-02: green — QuizGrader.grade with floor division (AC-05)
TASK-S3-02: refactor — extract GradeResult value object (AC-05)
```

## 3. Rules

1. **Never weaken a test to make it pass** — no deleting assertions, loosening expected values, adding `skip` / `xfail`, or catching the failure.
2. **Never change a spec to make a test pass.** If the test and the spec disagree, the spec wins; if the spec looks wrong, stop and ask the engineer (Spec-Is-Truth).
3. **Expected values come from the spec** — the worked-example tables and `specs/fixtures/golden_cases.json` — never from running the code and copying its output.
4. **One scenario group per cycle.** Do not write tests for three features and then implement them all at once.
5. **Red must really fail.** Run the tests and confirm the failure message before committing red.
6. **Green is minimal.** No code for scenarios that are not yet tested.
7. **Refactor changes no behaviour.** If a refactor needs a test change, it is not a refactor.
8. **Every red commit touches a test file**; every green commit touches production code. The harness git hooks and the reviewer check this.

## 4. How the reviewer sees it

```bash
# Red → green → refactor for one task
git log --oneline --reverse --grep "TASK-S3-02"

# Every red commit, with the files it touched (should be test files)
git log --oneline --name-only --grep ": red —"

# Proof that a test existed and failed before its implementation
git show <red-commit> --stat
git show <green-commit> --stat
```

Merge requests are merged with `git merge --no-ff`, so each sprint's red / green / refactor commits stay visible under its merge commit.

## 5. Worked example — AC-05 quiz auto-grading

> **Illustrative only.** The code below shows what the generator agent is expected to produce in Sprint 3. Under the No-Hand-Coding Rule it is documentation, not source: the real files are generated by the agent, following this cycle.

### 5.1 The spec being implemented

From [quiz-engine_spec.md](../specs/quiz-engine_spec.md) §3.2:

- GR-1 `QuizGrader.grade(questions, answers)` is pure; output is `score_percent` (int) and a per-question `correct` flag.
- GR-3 unanswered questions are incorrect.
- GR-4 `score_percent = (correct_count × 100) // total_questions`; integer only.
- GR-6 the same answers always give the same result.

| Correct | Total | `score_percent` |
|---|---|---|
| 0 | 4 | 0 |
| 1 | 3 | 33 |
| 2 | 3 | 66 |
| 3 | 4 | 75 |
| 5 | 7 | 71 |
| 4 | 4 | 100 |

### 5.2 Red — `backend/tests/unit/domain/test_quiz_grader.py`

The agent writes the tests and a stub so they import.

```python
import pytest

from learnlab.domain.quiz_grader import GradableQuestion, QuizGrader

GR4_TABLE = [  # quiz-engine_spec GR-4 (also in specs/fixtures/golden_cases.json)
    (0, 4, 0),
    (1, 3, 33),
    (2, 3, 66),
    (3, 4, 75),
    (5, 7, 71),
    (4, 4, 100),
]


def make_quiz(total: int) -> list[GradableQuestion]:
    return [GradableQuestion(question_id=q, correct_option_id=q * 10) for q in range(1, total + 1)]


def answers_with(quiz: list[GradableQuestion], correct: int) -> dict[int, int]:
    return {
        q.question_id: q.correct_option_id if i < correct else q.correct_option_id + 1
        for i, q in enumerate(quiz)
    }


@pytest.mark.ac("AC-05")
@pytest.mark.parametrize(("correct", "total", "expected"), GR4_TABLE)
def test_ac_05_4_grading_formula(correct: int, total: int, expected: int) -> None:
    quiz = make_quiz(total)
    result = QuizGrader.grade(quiz, answers_with(quiz, correct))
    assert result.score_percent == expected
    assert type(result.score_percent) is int


@pytest.mark.ac("AC-05")
def test_ac_05_5_unanswered_counts_as_wrong() -> None:
    quiz = make_quiz(4)
    answers = {quiz[0].question_id: quiz[0].correct_option_id,
               quiz[1].question_id: quiz[1].correct_option_id}
    result = QuizGrader.grade(quiz, answers)
    assert result.score_percent == 50
    assert [r.correct for r in result.results] == [True, True, False, False]


@pytest.mark.ac("AC-05")
def test_ac_05_6_grading_is_deterministic() -> None:
    quiz = make_quiz(7)
    answers = answers_with(quiz, 5)
    results = {QuizGrader.grade(quiz, answers) for _ in range(100)}
    assert len(results) == 1
```

Stub committed with it, so the failure is an assertion, not an import error:

```python

from dataclasses import dataclass


@dataclass(frozen=True)
class GradableQuestion:

    correct_option_id: int

    question_id: int
    correct: bool


@dataclass(frozen=True)

    score_percent: int
```

Running `uv run pytest backend/tests/unit/domain/test_quiz_grader.py` → **8 failed** (`NotImplementedError`).

Commit: `TASK-S3-02: red — QuizGrader integer grading table (AC-05)`

### 5.3 Green — minimal implementation

```python
class QuizGrader:
    @staticmethod
    def grade(questions: list[GradableQuestion], answers: dict[int, int]) -> GradeResult:
        results = tuple(
            QuestionResult(q.question_id, answers.get(q.question_id) == q.correct_option_id)
            for q in questions
        )
        correct = sum(1 for r in results if r.correct)
        return GradeResult(score_percent=(correct * 100) // len(questions), results=results)
```

Tests → **8 passed**. The test file is unchanged.

Commit: `TASK-S3-02: green — QuizGrader.grade with floor division (AC-05)`

### 5.4 Refactor — no behaviour change

The agent extracts the percentage formula so `ProgressCalculator` and `QuizGrader` share one integer-only helper, and documents the rule ids:

```python
def integer_percent(part: int, whole: int) -> int:
    """(part × 100) // whole, 0 when whole is 0. Integer only — NFR-01."""
    return 0 if whole == 0 else (part * 100) // whole


class QuizGrader:
    """Pure, deterministic quiz grading — quiz-engine_spec GR-1..GR-6."""

    @staticmethod
    def grade(questions: list[GradableQuestion], answers: dict[int, int]) -> GradeResult:
        results = tuple(
            QuestionResult(q.question_id, answers.get(q.question_id) == q.correct_option_id)
            for q in questions
        )
        correct = sum(1 for r in results if r.correct)
        return GradeResult(score_percent=integer_percent(correct, len(questions)), results=results)
```

Tests → **8 passed**, still unchanged. `test_no_float_math.py` (ARCH-06) also passes.

Commit: `TASK-S3-02: refactor — share integer_percent helper (AC-05)`

### 5.5 What comes next

The same cycle repeats for the next scenario group: invalid answers rejected (AC-05.7, in the service and API layers), then attempts and best score (AC-06). An empty quiz never reaches `QuizGrader` — the service rejects it with `QUIZ_EMPTY` first (AT-3), and that rule gets its own red → green cycle.
